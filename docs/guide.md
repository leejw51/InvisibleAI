# Invisible AI guide

The complete user and operator guide. The short overview is in the [README](../README.md); protocol details are in [PROTOCOL.md](../PROTOCOL.md).

Private help while you keep working: a Rust backend on your Mac Studio, a lightweight capture CLI on your Mac, and a web interface on your iPad. The key point: the on-device AI does the polling and the judging, and cloud AI (API, Codex, or Claude Code) is called only when it is actually needed. Choose **On-device**, **Hybrid**, **Cloud AI** (API keys), **Codex** or **Claude Code** (the `codex` / `claude` command-line tools signed in on the backend Mac, billed to those subscriptions). Turn on **Auto** to get help in a TextEdit or Apple Notes note, send requests to the Mac from your iPhone or iPad (Safari, web search, calculator, questions), or use **Capture** for one screen.

![Invisible AI's lavender companion floating above an open notebook with orbiting notes and a photo](../frontend/assets/invisible-ai-hero.png)

Start with the [Invisible AI setup and limitations](invisible-ai.md). Auto starts off; Hybrid sends a note to cloud AI as soon as the local model asks for help, or asks first when **Ask before each cloud request** is on. Apple Foundation Models, Apple speech recognition, and MLX adapters are available. The Wiki holds only what is worth remembering, in organized form, by type: **q&a**, **note** (kept text tidied by your AI, with the original one tap away), **code**, **photo**, **video**; the chat keeps the raw conversation. Pictures and clips added on the Images and Videos pages get cached thumbnails and are filed in the Wiki as photos and videos, and Apple Vision names what it sees in a picture or a video frame as hashtags. **Videos** lists every uploaded clip like a file box: upload by button or drop, play in place (the backend streams with Range support so seeking works on iPad), search by name, download or delete. The Wiki map has zoom buttons and its own fullscreen; one tap on a message node reads it in place, and one tap on a photo or video node shows or plays it. In the feed, one tap on a thumbnail shows the picture or plays the clip over the page, and one tap on a title reads the message; a big **Back** (or Esc) closes the top layer and leaves the feed, map, scroll and search exactly as they were. An open tag has a **Close** button beside its name that brings back exactly the screen the tag was opened from: the earlier tag or search, the feed or the map, a message you were reading, and how far down the page was; a tag opened over a tag steps back one at a time. **Delete tag** (beside Show everything, with a confirmation) removes the open tag from every message for good; the messages stay. **Delete all** under **Settings** in the main menu is the right to be forgotten: after a confirmation it erases every message, memo, picture, video, file, Wiki tag and document, code note and cached thumbnail of your account on the backend; your login stays. The search box suggests earlier searches that found something, and matching tags, after the first letter. **Code** shares everything kept with fenced code function by function: each card shows Input (the parameters), Output (the return type), the code to copy, and a note of your own, with search, language chips and a link back to the Wiki message. **Wiki** tags every saved message (on-device in On-device and Hybrid modes, with your cloud model only in Cloud AI mode) and organizes them by tag, with BM25 plus semantic search, a tag map, related messages, and a fullscreen mode. Every message leads with a category (personal, q&a, information, idea, task or other): a question and its answer are one q&a node, and a line that reads like a record (a diary note, a fact, a link, a to-do) is kept as a note: the AI tidies it into a clean, structured version instead of answering, both are saved and tagged into the Wiki, and **Ask AI instead** is one click away. In a chat room, each message you post and the response generated for it show their category and automatically generated tags under the text as soon as they are inferred from both; a tag opens it in the Wiki on the second tap (the first only highlights it, so a stray touch stays in the chat), and **Edit tags** on either message adds or removes tags in place, which the Wiki and every device follow. Open **Assistance settings** to configure Wiki and TextEdit for your account. AI research synthesis and encrypted peer communication remain in [the work plan](../TODO.md).

## Run

Requires macOS for Apple Vision OCR and screen capture, Apple Command Line Tools, Rust 1.90+ managed by rustup, and Node.js 22.13+ with npm (including `node:sqlite` for integration tests). `make install` adds the Rust WASM target, rustfmt, Clippy, Trunk when missing, locked Cargo/npm dependencies (including build/test packages), and Playwright Chromium and WebKit. `make setup` remains an alias. Rust's `rustc` must be installed on the backend for compilation. Build tools use Node; application logic is Rust.

```sh
make install
cp .env.example .env
# Edit .env on the backend: set CWBBOT_ADMIN. Cloud keys are optional for local AI.
make start
make status
make stop
```

`make` shows help. `make start` builds the frontend and backend, then starts only the backend. `make start2` builds and starts both the backend and Rust capture client. `make start3` builds and starts only the Rust capture client; set `BACKEND_URL` to connect to a remote backend. `make start-server` and `make start-client` remain aliases for `start` and `start3`. These commands keep current processes running and automatically restart a backend or capture client when its build changes; `make stop` stops both managed processes and the on-device workers (the backend shuts its MLX worker down on SIGTERM or Ctrl-C, and the script sweeps any worker or server from this checkout that an earlier build left behind); `make stop3` stops only the Rust capture client and leaves the backend running. `make start` binds the backend to **0.0.0.0:3000** so LAN and Tailscale devices can connect, as long as wallet sign-in (`CWBBOT_ADMIN`) or `APP_TOKEN` is configured. Without either, it falls back to 127.0.0.1:3000. Set `BIND_ADDR=127.0.0.1:3000` to keep it on this Mac. The bare `server serve` command still defaults to 127.0.0.1:3000. Startup prints the listening address, separate **Web URL** (`http://HOST:3000`) and **API URL** (`http://HOST:3000/api`) entries for localhost, LAN, and detected Tailscale addresses, plus API health and Tailwind CSS URLs. Use the printed LAN or VPN host address on remote devices. Tailwind is compiled and served locally; there is no runtime CDN dependency. Backend logs are in `~/.causewaybaybot/logs/`; capture-client logs are in `~/.causewaybaybotclient/logs/`.

For the three-computer setup:

Startup waits for the backend's ready message and checks whether the capture client remains alive. It reports the capture process's startup Screen Recording permission check, whether it connected or is still retrying, and its log path. Repeating `make start2` also prints the existing backend's Web URLs and client status. A client that exits during startup or a backend that does not become ready makes the command fail instead of silently reporting success. A running client may keep retrying an offline remote backend. Screen Recording permission belongs to the app that launched the client; allowing Codex does not establish permission for a client launched from Terminal or iTerm.

```sh
# Mac Studio
make start

# MacBook (a checkout with Rust installed)
make start3 BACKEND_URL=http://STUDIO-VPN-IP:3000

# Or use the packaged capture binary:
./bin/client http://STUDIO-VPN-IP:3000
```

Replace `backend.example` with your backend's LAN/VPN hostname or IP address, then run `rust-cli http://backend.example:3000` (or `./bin/client` from the extracted package). The client saves the backend URL and owner wallet before connecting. Later, running `rust-cli` (or packaged `./bin/client`) alone reconnects using the saved settings, including the same node identity and computer name. With no saved connection, it shows connection instructions; `--help` always shows help. `rust-cli client --backend URL --name NAME` exposes advanced options. The default node name comes from the computer's system name. Source builds also provide `causewaybay` and `rust_cli` compatibility aliases.

```sh
# Only this approved wallet can capture from the node (admins cannot bypass ownership):
rust-cli http://backend.example:3000 0xYOUR_OWNER_WALLET_ADDRESS

# Share this node with every approved user in the VPN workspace:
rust-cli http://backend.example:3000
```

The URL shortcut without an owner explicitly selects shared access. `client --owner-wallet ADDRESS` and `client --shared` are the equivalent advanced options; `client` without either restores its saved owner from JSONL. Starting with no arguments also preserves the saved owner or shared-access setting:

```sh
# Reuse the last connection's URL and owner wallet:
rust-cli
```

Settings are stored in `~/.causewaybaybotclient/client.jsonl`, or in `CAUSEWAYBAY_CLIENT_CONFIG_DIR` when set. The optional `APP_TOKEN` stays in the environment and is not saved with the connection.

Open the Studio's printed VPN URL on the iPad. Choose the MacBook in the capture selector. Grant **Screen Recording** permission to the MacBook terminal or executable in macOS System Settings → Privacy & Security, then restart the client if macOS requests it. Full-display capture works remotely; **Region** capture opens an interactive selector on the MacBook and needs someone there to select a region.

The CLI holds a JSON WebSocket connection, sends heartbeats, and sleeps before reconnecting when disconnected. Backend callbacks arrive over a separate reconnecting HTTP SSE stream; captures and JSON request/response messages use WebSocket. The browser receives memo progress and answers through SSE with durable event IDs. The browser waits **two seconds between reconnect attempts**, detects stale connections with heartbeats, and resumes saved response events. Its top bar shows **Connecting**, **Connected**, or **Reconnecting**. The Studio performs OCR and cloud calls; the MacBook only captures on request.

`make start` rebuilds the web client and backend. If the managed backend is running an older build (or predates build tracking), it restarts that backend so the login API matches the web client. Repeating the command with an unchanged backend build keeps the existing process. The backend runs independently of the launching terminal. Account data and capture clients are preserved.

## Use

Use the language selector in the top bar (also available before login) for **English, 한국어, 廣東話, 简体中文, 日本語, Español, or Čeština**. Cantonese uses Traditional Chinese with Cantonese wording; Chinese uses Simplified Chinese. The choice applies immediately and is saved as `causewaybay.language.v1` in browser local storage for this site, independently of wallet and server settings. Other tabs on the same site update automatically. English is the default and the fallback for invalid saved values. If browser storage is blocked, the choice still works for the current session and the UI explains that it could not be saved. Changing the interface language preserves chat drafts, attachments and live subscriptions; stored names, messages, AI answers, code and uploaded content keep their original text.

The labeled **Light / Dark** button next to the language selector switches appearance on desktop, iPad, and iPhone, including before login. It stays reachable in the sticky header and has a 44-pixel touch target. The theme is saved as `causewaybay.theme.v1` in web local storage and updates across tabs. It is applied before the page renders to avoid a light flash on reload. Tablet portrait and phone layouts use a navigation drawer; controls respect safe-area spacing, and touch inputs use readable sizes that avoid Safari's automatic input zoom.

**Active capture device** selects one Rust client for a new chatroom. The first capture or TextEdit start binds that computer to the room; manual captures and optional polling keep using it after reloads and backend restarts. Create a new chatroom to capture another computer. Device defaults remain browser preferences for new rooms. If a bound computer disconnects, capture waits for that computer instead of silently switching.

The web client shows a floating glass-orb animation while opening the workspace and reconnecting. A successful connection triggers a checkmark reveal that fades after four seconds; the top-bar connection indicator keeps a subtle heartbeat while connected. These states follow actual WebSocket ready/close events. The reconnect card does not intercept input, and all connection movement stops when the browser prefers reduced motion. The artwork is generated with the built-in image generation tool; its prompt is saved in `frontend/assets/connection-orb.prompt.txt`.

The Devices page lists the backend's detected **Local access**, **Network access**, **Tailscale DNS**, and **Tailscale IP** Web/API addresses, each with a Copy button. The wallet-specific Rust connection command also has a Copy button and prefers the Tailscale IP, then Tailscale DNS, then LAN. Discovery uses the backend's actual listening port and runs on backend startup; restart the backend after changing its network configuration. A localhost-only listener does not advertise remote interfaces.

**AI settings** (`/ai`, at the bottom of the sidebar) is the one place to choose which AI answers: the mode (On-device, Hybrid, Cloud AI, Codex, Claude Code), the provider and the model. The pick is saved in this browser's local storage and mirrored to your account, so Chat, Coding and Autonomous AI sessions all follow it, and the same picker is embedded in Chat's **AI & tools** panel and in Coding's **AI for this work**, so it can be changed wherever AI is used.

**Capture is already the request.** With no typed prompt, the AI solves coding quizzes and writes code, solves math, evaluates ideas and their tradeoffs, explains messenger context and next actions, and answers questions in photos or diagrams. It asks a follow-up only when essential information is missing. Conversation captures explain context before any optional suggested reply.

New chats default to **Image mode**, so one-click Capture includes visual information needed for photos, diagrams, and code. An explicitly saved Text mode choice remains respected; Text mode sends extracted text only. Both modes infer the task automatically without a separate question or Send step.

**New thought** is the one place to put anything: type, paste a picture, or drop files (Markdown, pictures, videos, audio, PDFs, Office documents) anywhere on the page, then press Enter. Everything is kept as a memo, indexed for BM25 and semantic search in SQLite, tagged and organized into the Wiki (tag documents are rows in the same SQLite database), and used as context for later questions in that chat. With an enabled AI provider, Enter also asks it; without one, Enter keeps the thought. **Save memo** keeps the original text and files without adding an AI reply to the chat. File text (document text, Apple Vision text of pictures and one video frame, a local transcript) is read on the backend. Background tidying and Wiki tagging use the account's selected AI policy: On-device and Hybrid keep this work local; Cloud AI permits cloud processing. Without a usable model, the raw memo remains available. Hashtags written inside a kept document become the memo's tags. **New thought** and **New chat** start an independent conversation, clearing the draft and staged attachments. Reloading resumes the current thought; use the room picker to return to an earlier conversation. AI context in a chat includes only that room’s messages and supplied files; library answers are not automatically injected. Click **Capture** for one screenshot and one automatic answer. Click **Multi Capture** repeatedly to stage up to eight screenshots/photos/files, then **Send message** (or Enter) to send them together for one response. The bottom toolbar always shows **Capture · Text prompt · Multi Capture · Send message**. Cancel exits Multi Capture and keeps the staged attachments available to send. Type a follow-up and press Enter to continue. Shift+Enter inserts a new line. Choose the AI provider and model in the chat's **AI & tools** panel, the one place for that choice. The provider is saved to your account, so every device uses it; the model name is remembered per browser; API keys stay on the server. The AI processing mode (On-device, Hybrid, Cloud AI, Codex, Claude Code) is chosen on the **Autonomous AI** page; New thought shows the current mode with a link there. **More tools → Multi-device capture** retains the multi-computer batch workflow at `/overview`, and **More tools → Quiz playground** opens the capture test page; ordinary coding, math, and search questions work directly in chat. **Search your notes** opens private library search; **Devices** provides the connection command for your current server and wallet. Menu pages and saved memo links support reload and browser Back/Forward.

Rust clients send the full captured image to the backend. Web previews use JPEG thumbnails with a maximum edge of 960 pixels, lazy loading, and asynchronous decoding for faster responses; click any thumbnail to open the full-resolution original. This applies to chat, uploaded photos, memo previews, and the image library. Thumbnails are generated on demand without storing extra files, so deleting an image or clearing its chatroom leaves no thumbnail artifact.

Every conversation uses messenger-style bubbles. **Copy** on a message copies its full text, including code, extracted text, transcripts, attachment names, and sources. Each code block has **Copy** for only that code; **Copy all** copies the text of every visible, non-deleted message in the room in order. You can edit or remove user and AI messages, rename a room, clear it, or delete it. Changes synchronize to your other devices using stable message/room GUIDs and monotonic, time-derived int64 revision IDs. Concurrent edits show a conflict instead of overwriting another device's change.

Ordinary chat can use arithmetic, provider-native web search with sources, and your private note/file search automatically. Coding answers include formatted code; **Allow file creation & compilation** in the chat's AI & tools panel is the only agent control and additionally permits saving file versions and compiling Rust.

- **Dashboard** (at `/dashboard`; the older `/status` address still opens it) shows your memos, pinned notes, files, images, chatrooms, messages, stored media, running/failed requests, capture queue, and live devices. Admins can switch to system totals, registered wallet roles, all web/Rust clients, provider configuration, and search status. The Three.js diagram uses exponential tweening and cosine motion, honors reduced motion, and keeps all statistics readable without WebGL. It refreshes every three seconds.
- **Devices** (at `/devices`) shows backend status/uptime, connected Rust capture clients and web browser tabs, device names, platforms, and last-seen times. It refreshes automatically every two seconds. Browser tabs keep the same identity across reconnects; recent offline tabs are collapsed. The backend exposes the same snapshot as JSON at `/api/devices` (and the older `/api/dashboard`) and logs Rust/web connection counts when clients join or leave. On a backend outage, the UI marks cached connection information unknown until it reconnects.
- **Capture:** choose one computer, select multiple computers, or choose **All connected clients**. Each selected Rust client captures its screen and sends the PNG over WebSocket. Multiple captures start together and show separate named results; cloud generation runs up to four jobs concurrently. The web page shows the screenshot immediately, with Capture → OCR/Image → AI progress. The image stays visible if OCR or AI fails.
- **Rename computers:** click **Rename** beside a Rust client in Devices. The backend saves the alias in `nodes.jsonl` and sends it over SSE; the client saves its name to `~/.causewaybaybotclient/client.jsonl`. Offline clients receive their updated name when they reconnect.
- **Quiz playground** (also `/quiz`): randomized arithmetic plus Rust quicksort, sliding-window, and producer/consumer challenges. **New numbers** changes the current question; **Random quiz** chooses a category. Reveal the expected result or use **Capture this quiz**, which hides the answer and keeps the question visible. Open this page on the computer whose screen you capture.
- **Text mode:** capture → Apple Vision OCR on the backend → send extracted text to your chosen AI provider.
- **Image mode:** capture → send a resized screenshot directly to a vision-capable cloud model. The original remains on backend disk with a relative path in SQLite.
- Ask a question without a capture, attach an image or text file, or ask a follow-up.
- Comments and conversations receive suggested replies. Code receives a solution with fenced code blocks. Questions receive direct answers.
- Use **Library** (under **More tools**) to search, filter, pin, delete, or export Markdown. Combine terms and tags, for example `borrowing #rust`. **Pinned** is a filter tab inside the library.
- The coding agent (**Allow file creation & compilation** in a chat) can list/read files and notes, OCR an image, write or edit a versioned file, search/save memos, fetch a public web page, and compile Rust. Tool calls and results appear with the response and are saved. Whole programs that build and run live on the **Coding** page; the ones published as skills can be run from any chat with `run_skill`.
- **Chat** rooms are also backend sessions. Memos, captures, OCR text, attachments, TextEdit replies, and streamed answers use the same history and context. **Save memo** records text without invoking AI. **Capture** takes a screenshot on the room's single capture computer; chatrooms have no periodic capture setup. Backend session controls live in **Autonomous AI** (at `/autonomous`; the older `/cloud` address still opens it): choose one capture computer, use **Capture now**, set an interval, and **Start polling / Stop polling**. An active chat links to **Manage in Autonomous AI**. **Capture** during polling queues a manual frame and resets the interval after it completes; captures never overlap. Unchanged decoded screenshots are discarded; an empty repeated frame adds no history or AI response, while explicit typed questions still receive an answer. Each AI response identifies **Local AI** or **Cloud LLM**, its provider, and model. Stop cancels the loop and pending work; backend restart preserves history and the computer binding but stops polling.
- **Files** and **Images** provide preview, download, and deletion. Text/Markdown/JSON, UTF-8/UTF-16, CSV, PNG/JPEG/WebP and audio are processed on the backend. Audio uses xAI speech-to-text or Gemini; raw binary files expose metadata and a short hex preview, not invented content. Rust files can be compiled. Processing and compiler results are saved in SQLite. Deletions update chat attachment references; existing OCR, transcripts, and answers remain.
- **AI server** in Chat shows the backend provider and model. Admins can use Check AI connection to make a small real inference request.

Configure API keys **only on the backend computer**. Copy [`.env.example`](../.env.example) to `.env` in the project/package directory and set `XAI_API_KEY` for Grok. You can instead export the key in the server's environment, or put a `.env` file in `~/.causewaybaybot/` (the `--config-dir` / `CAUSEWAYBAY_CONFIG_DIR` directory if changed). Supported names:

```dotenv
XAI_API_KEY=your-xai-key
# Optional alternatives:
# ANTHROPIC_API_KEY=your-anthropic-key
# OPENAI_API_KEY=your-openai-key
# GEMINI_API_KEY=your-gemini-key
```

The backend loads its working-directory `.env`, then its configuration-directory `.env`, before starting worker threads. Existing environment variables win, including explicitly empty values; the working-directory file takes precedence over the configuration-directory file. Restart the backend after changing keys. Real `.env` files are ignored by Git; `.env.example` contains no credentials and is included in the release package.

**No API-key setup is needed in the web client or capture CLI.** Grok is automatically selected when only `XAI_API_KEY` is configured. With multiple providers, a saved available provider is preferred, then the first configured provider. Settings shows which providers are available; choose a model supported by your account. Admins use **Save backend settings** in the web Settings dialog to save the server-level provider, model, input mode, and capture defaults in `~/.causewaybaybot/settings.jsonl`; the server restores them on restart. Per-account AI mode lives on the Autonomous AI page. Browser localStorage keeps personal selections and drafts. Chat message records are cached only in IndexedDB, in a database scoped to the signed-in wallet. Every room/message has a GUID; an int64 `messagesyncid` is the server replay cursor. Message JSON stays a string in IndexedDB to preserve int64 values exactly. Images/files remain on the backend. Any keys stored by an older browser version are removed on load. Browser requests cannot supply or modify provider keys; keys are never sent to the browser or saved to SQLite/JSONL. Older encrypted database credentials are no longer used.

When the same wallet signs in on another device, **New thought** resumes the shared current thought. Starting a new thought on either device updates other New thought screens through SSE and clears their previous drafts and staged captures. Chatroom creation, renaming, clearing, deletion and messages also sync through SSE. A device viewing a selected saved chatroom stays in that conversation. Reconnecting reconciles the latest state, including changes made while that device was disconnected.

## Wallet login and approval

Set `CWBBOT_ADMIN=0x...` in the backend environment or `.env`. This wallet is the permanent owner. The login page accepts a BIP-39 recovery phrase and **Wallet index** (default `0`, range `0–2147483647`), deriving `m/44'/60'/0'/0/{index}` and signing a one-use, host-bound EIP-191 challenge. A different index selects a different wallet, with its own approval and private workspace. No blockchain transaction is needed. **Create new recovery phrase** generates 12 words (or 24, selectable) locally using browser cryptographic randomness. The words stay hidden until the user presses **Show recovery phrase**, which lists them numbered for writing on paper; **Copy recovery phrase** copies them instead. The user must acknowledge saving both the ordered words and wallet index before signing in. The phrase is never transmitted or persisted; only the derived private key is kept, in this browser's local storage.

A new wallet can sign in but sees only the waiting page and its account details. Its first successful login automatically registers it under **Admin → Waiting for approval**. The login page suggests a deterministic wallet-derived user name that the user can edit. Saved names are retained on later logins unless explicitly changed. Admins approve, decline/block, promote approved users to admin, or demote admins. The environment owner cannot be demoted through the UI/API. Every HTTP, WebSocket, and SSE workspace request requires approval. Roles are rechecked on active connections, so revocation takes effect without waiting for a session to expire. Only admins see the Admin menu, backend settings, or node-renaming actions, and the backend enforces these permissions. Changes append an audited snapshot to `users.jsonl` and update SQLite.

Sessions use random HttpOnly, SameSite cookies; only token hashes are stored in SQLite. On HTTPS, login cookies also have Secure. The app serves HTTP/WS within the trusted VPN and supports HTTPS/WSS behind a proxy. Each normalized wallet address is the permanent account key. Display names default to a deterministic name and can be changed through **Account details → Save name**, including while waiting for approval. Names are labels, never authorization identifiers, and are saved to the audited user snapshots. Rooms, messages, memos, files, captures, search results, and browser presence are private to that wallet; administrators cannot read another wallet's content through the API. Shared capture hardware may be explicitly configured, but the resulting data belongs to the requester. There is no public-content endpoint. Legacy records without an owner remain in the local account and are not assigned to an arbitrary wallet during migration.

**Account details → Show recovery details** asks for confirmation before displaying the original recovery phrase and wallet index. Details hide after one minute, when the tab loses visibility, or when the dialog closes. The phrase stays only in the current tab’s memory until a reload or sign-out; after a reload, the user must re-enter it and confirm before seeing it again. The browser verifies that the re-entered phrase matches the signed-in wallet at its session’s index. Neither admins nor the backend can recover a lost phrase. The non-secret wallet index is retained in the authenticated session, including after a reload.

`APP_TOKEN` optionally protects capture-node connections. Set the same value on the backend and in the CLI environment. In wallet mode it cannot grant browser/admin access. Without it, Rust clients can connect within the trusted VPN. With `CWBBOT_ADMIN` unset, the previous local/demo or access-token mode remains available; configure the admin wallet for approval-controlled access.

## Autonomous AI sessions

Autonomous AI and Chat share the same room IDs, messages, storage, and context. **Autonomous AI → Open chat history** opens the corresponding chatroom, including capture thumbnails and saved memos. `/api/invisible/sessions` (the API keeps its older name) is a session view of those rooms, with optional TextEdit controls; it does not maintain a second conversation. Each card's **Progress** panel shows the current step with a live animation, which LLM is running and whether it is a local LLM or cloud AI, the running wait time, every recorded step, and recent AI requests with wait, tokens and an estimated cloud cost. **New session** suggests a random name, and **Create and start** begins TextEdit replies immediately. Each card leads with the **Autonomous AI run** with its own watched app (detected automatically among **TextEdit**, **Apple Notes (메모)** and **Terminal** from the app in front, or pinned to one, or remote prompts only; in a terminal, an entered `ai- question` is answered in place as display output; no command is ever sent to the shell), check interval, typing pause and answer length, and a large Start/Stop; **Manual capture** is a collapsed add-on with Capture now and optional polling. Everything the AI touches, including uploaded files, pictures and video (shown by one frame), is saved as a memo in SQLite and organized into the Wiki with its cloud token use and estimated cost recorded; the schema migrates itself when tables change. Unchanged notes never call a model, and in Cloud AI, Codex, or Claude Code mode the local model first decides whether a changed note asks for help before anything leaves the Mac. **Read from the screen** (default on) attaches a screenshot of the Mac to each note answer so the AI reads the note as displayed, locally via Apple Vision for local AI or as an image for cloud AI. **Remote control** on the same card lets an iPhone or iPad drive the Mac through a running session: `open youtube.com` opens Safari, `search …` opens a web search, `calc 12*34` or plain arithmetic computes on the backend, and any other request is answered by the configured (on-device by default) model, which may request Safari or calculator actions that the backend validates first. Unchanged screen text never triggers a model. A **Processing stats** strip on the Autonomous AI page counts OCR runs, local LLM and cloud AI requests (with tokens and estimated cost) and skipped screens, refreshed after every AI job. In chat, a running reply shows an animated waiting row with the LLM, whether it is local or cloud, and the seconds waited, and each finished reply logs **Answered by Local LLM** or **Answered by Cloud AI** with the provider and model. Closing the UI or logging out leaves started workers running. Backend restart preserves history and imports older room-owned TextEdit memos into chat history; explicitly restart workers to resume capture or document input. See [session APIs and lifecycle](invisible-ai.md#backend-owned-sessions).

## Storage and search

```text
~/.causewaybaybot/              # backend computer
  .env                         # optional backend-only credentials
  backend.jsonl                # server address and static asset location
  settings.jsonl               # AI/capture defaults editable from the web UI
  nodes.jsonl                  # computer names managed by admins
  users.jsonl                  # approved/pending/blocked users, roles and audit snapshots
  data/causewaybay.sqlite3      # messages, metadata, relative paths, sessions, search
  data/screenshots/<memo>.png   # original screenshot (or .jpg/.webp for uploads)
  data/files/<id>/<name>       # uploaded binary media (pictures, video, sound, PDFs, archives)
  data/models/                 # cached local embedding model
  data/wiki/<wallet-hash>/      # readable Wiki Markdown tag documents
  logs/                        # backend logs
  run/                         # managed server PID

~/.causewaybaybotclient/        # capture computer
  client.jsonl                 # backend URL, identity, owner wallet, name, retry interval
  screenshots/<request-guid>.png       # actual screen captures with normal PNG filenames
  logs/                        # capture-client logs
  run/                         # managed client PID
```

All application-owned persistent backend data defaults to `~/.causewaybaybot/`, independent of the launch directory. The storage location is not a web setting and is never saved as an override in `backend.jsonl`. Back up this complete folder while the backend is stopped. Apple-managed model assets and separately installed MLX services remain managed by their respective runtimes.

Explicit backend launch overrides (`CAUSEWAYBAY_CONFIG_DIR`, `--config-dir`, `make CONFIG_DIR=/some/path`, and `--data-dir` / `DATA_DIR`) remain available for isolated tests and deployments; they are not remembered on the next launch. If an older saved data location contains an archive outside the default, startup stops with migration instructions rather than silently opening an empty archive. Move the complete old data folder to `<backend folder>/data` while stopped; do not merge two archives. No automatic move or deletion occurs. For the Rust client, use `CAUSEWAYBAY_CLIENT_CONFIG_DIR`, its `--config-dir` flag, or `make CLIENT_CONFIG_DIR=/some/path`. Defaults remain separate even on one computer. Each JSONL line is a versioned snapshot; the last valid record wins, and interrupted appends are ignored. Secrets are excluded. Run either binary with `--help` for all flags.

Search combines exact hashtag filters, SQLite FTS5 BM25, and cosine similarity from local multilingual **paraphrase-multilingual-MiniLM-L12-v2** embeddings using reciprocal-rank fusion, so a question in English finds a note kept in Korean and the reverse. Keyword search also tries Korean words without a trailing particle. Notes indexed by an older embedding model are re-indexed automatically. In chat, notes you saved yourself are shared with the AI only when they closely match the question; earlier AI answers never are. The first model load downloads weights; indexing then runs locally in the background. The UI reports availability and falls back to BM25 + tags during loading or failure. Use `SEMANTIC_SEARCH=off` to disable it. SQLite holds every piece of text: memos and answers, chat messages, Wiki tags and tag documents, code notes, and the content of every text file (documents, Markdown, JSON, CSV, code) in the `files.text` column, so one database file is the complete, searchable record of what was written or kept, ready for export or fine-tuning. Only binary media (screenshots, pictures, video, sound, PDFs, archives) lives on disk under `screenshots/` and `files/`, with its relative path in SQLite. Existing installations are migrated on startup: text files written to disk by an earlier version move into SQLite, and the old `markdown/` and `wiki/` Markdown mirrors (derived copies) are removed. Back up the SQLite database and the media folders together: missing media cannot be reconstructed from SQLite. `/api/memos/{id}/export` renders a memo as Markdown on demand. Deleting a memo removes its backend screenshot. Individual memo deletion is separate from clearing an entire room; room cleanup also removes room-owned attachments and requests erasure of the client originals. Back up the backend folder while the server is stopped. Manage the backend environment or `.env` credentials separately.

### Clearing and deleting rooms

**Delete all**, available in New thought and chatrooms, asks for confirmation before erasing all saved content belonging to the signed-in wallet across every room and the standalone library. It cancels pending answers and continuous capture and deletes notes, images, files, generated output, search indexes, old revisions, and cached conversations. Other sessions update through durable notifications; offline or signed-out sessions reconcile when they reconnect or log in again. A room opens from the authoritative server snapshot before showing messages, so stale browser text does not flash during reconciliation. Login and account approval remain active, and other users' data is preserved. Interrupted erasure resumes at startup before accepting new content. The same client-original and backup limitations described below apply.

Clear preserves an empty room; delete removes it from the room list. Both cancel active work and remove room-owned messages and old revisions, OCR/transcripts, answers, notes, screenshots, uploads, generated files, Markdown exports, embeddings, processing/compilation results, and queued capture requests. Interrupted cleanup resumes on server startup. SQLite secure deletion, FTS cleanup and WAL truncation remove obsolete application records; this is not a forensic disk-wipe guarantee.

Removing a user message also removes its generated response, which may quote the prompt, and associated generated files/notes. Removing an assistant message removes that answer and its generated outputs. Attachments explicitly reused in another live message are preserved. Each edit replaces its previous replay snapshot; obsolete message versions and duplicate submission text are not retained. Clear creates a fresh `messagesyncid` barrier even for an empty room.

Content-free IDs/cursors remain so offline clients can learn what to erase. SSE notifications clear browser caches on any page and remove request-named screenshots from Rust capture clients when they reconnect. Independent downloads/backups and screenshots created by older clients with unrelated random filenames cannot be recalled automatically. Keep clients updated for this cleanup protocol.

Browser and Rust clients keep WebSocket connections for commands, uploads, and heartbeat. Reconnecting SSE streams carry answer changes, capture commands, and arbitrary targeted JSON notifications.

## Coding projects and skills

**Coding** (under **More tools**, at `/coding`) is where the coding agent writes real programs. A project is one folder under the backend's data folder (`projects/<uuid>`, shown on the page), scaffolded as a small real project: a Cargo crate for Rust, a Go module, `main.py` for Python, `main.c`, `main.lua` or `main.ts`, with a README, a `.gitignore` and a git repository when `git` is installed. The page lists which languages this backend can run and why one cannot (the Go, rustup, Anaconda, Xcode, LuaJIT/Lua and Node.js 22+ toolchains are detected once at first use; `INVISIBLE_PYTHON` overrides the interpreter).

Describe what the program should do and press **Build it**. The AI that does the work is picked right on the page (**AI for this work**, the same picker as **AI settings** and the chat). **Cloud AI** providers work with tools shaped after Claude Code's: list, read (numbered lines, offset and limit), grep (regular expressions, an `include` glob, case folding), glob, write, edit (a unique replacement tolerant of misquoted whitespace, or `replace_all` for renames; a file must have been read in the same request before it is edited or overwritten), delete, run the program, run the tests, run_command (one toolchain program at a time in the sandbox with no shell and no network: cargo, rustc, go, gofmt, python, pip, pytest, node, npm, npx, luajit, clang), a task list (`todo_write`, shown live on the page), publish a skill, and web search for documentation. The project's own `AGENTS.md` or `CLAUDE.md` is added to the instructions when present. The model's text streams to the page as it works, the same call repeated three times is refused as a loop, older tool results are pruned to stubs once the conversation grows past about 240 KB, and a request ends only after a real run (up to 30 steps and 80 tool calls). **On-device** models (and **Hybrid**'s local half) go through the backend's text harness, a protocol any model can speak (whole files in, build and run output back, workspace activity shown live). The harness is an agent: it keeps iterating, up to twelve rounds, until the program builds, runs and the model confirms the output, asks again when a reply brings a plan instead of files, accepts a plain fenced program from a local model as the entry file, answers `<<<READ path>>>` and `<<<GREP text>>>` requests so the model can look before it writes, runs the tests when asked with `<<<TEST>>>`, and only counts the request done after a clean run. In **Hybrid**, when the on-device model has not got the program running by the end, the cloud provider continues from the folder as it is (unless cloud help is set to ask first). **Codex** and **Claude Code** are run directly in the folder with their own tools: the folder carries a `CLAUDE.md` / `AGENTS.md` with the rules, their shells get the toolchain and in-folder caches so cargo, go, pip and npm work, their steps stream to the page as they happen, Claude Code keeps one session per project and resumes it on the next request (cheaper, and it remembers the folder), and the backend runs the result afterwards. There is a **Stop** button while the agent works; **Codex** and **Claude Code** are run directly in the project folder with their own tools switched on, inside a sandbox that keeps them to that folder, and the backend runs the result afterwards. The answer ends with the run result. Files can be opened and edited in place, **Build and run** runs the program again with any stdin, and the previous requests of the project stay listed.

Every build and run happens under `sandbox-exec`: no network, writes only inside the project folder (caches, virtualenvs, `node_modules` and binaries live in the folder, mostly under its hidden `.cache`), reads only from the toolchains, the system and that folder; stdout and stderr are kept to 64 KB each, a run is stopped after 60 seconds, a build after 300, tests after 180, and the whole process group is killed. **Package managers are allowed** with the same confinement: when `Cargo.toml`, `go.mod`, `requirements.txt` or `package.json` declares dependencies, a separate fetch step (`cargo fetch`, `go mod tidy` + `go mod download`, a project virtualenv with `pip install -r`, `npm install`) runs with the network on and every write still inside the folder; it repeats only when the manifest or lock file changes, and the build and run that follow are offline. C and Lua have no package manager here. **Run tests** runs `cargo test`, `go test ./...`, pytest (or unittest) or `node --test` in the same sandbox. Python runs with Anaconda's interpreter (or the project's virtualenv), TypeScript directly with Node's type stripping (no `tsc`).

The point of all this is **skills**: small command-line programs of your own (input on stdin and arguments, result on stdout, exit code 0 when it worked, no prompts or menus) that the chat AI can run. **Skills** (under **More tools**, at `/skills`) is where they are managed: **New skill** takes a name, a language, a one-line description and optional details, creates the project and sends the agent to build it; the skill is listed at once as *Building…*, then *Not running yet* or *Live* (live means its last run succeeded, and only live skills are offered to the chat). A skill counts as working when it runs cleanly on its **example run**: `example.json` in the folder (`{"args":[…],"stdin":"…"}`), which the form's *Example input* and *Example arguments* fields write, the agent writes itself when the program takes input, and you can edit like any file; when it is missing, the backend's input maker asks the picked AI to read the program and write one before the verification run, so a skill that takes arguments can go live without anyone typing an example. The workbench's Run box starts from it and **Suggest input** asks for a fresh one. Each card runs the skill with any input and arguments, renames or re-describes it, opens its code in the Coding workbench, retires it (the code stays a project) or deletes it with its code. Projects that are not skills yet are listed below with **Add as skill**. The coding agent is deliberately limited to this: it builds and refines skills in their own folders and nothing else, so the AI improves what it can do for you without touching the system it runs in. Three guard rails (after the Hermes agent's skills system) keep that from degrading: every agent request, save and delete is a **checkpoint** (a git commit in the folder) that the workbench can revert to, so nothing the agent does is final; every use from a chat or the Skills page lands in a **ledger** (runs, failures, last error, shown on the card) without ever taking a live skill offline, and a failed use offers **Fix with the agent**, which opens the workbench with the failure quoted; and the library is capped at 200 skills, with the chat told about at most 50 live ones. In chats with a tool-capable provider the AI gets a `run_skill` tool whose description lists the account's live skills; a call runs the skill in the same sandbox with the model's text on stdin (and arguments) and returns the output. You can see it happen: the chat's AI & tools panel names the skills available to that chat, a reply that used one carries a **Skills used** line with each name and whether it ran cleanly (also on the memo page), and the skill's card counts how often the chat AI used it. Retiring a skill or deleting its project removes it from the catalogue.

## Coding harness

The implementation uses a shared tool catalogue and bounded provider/tool loop. All providers use their native streaming/tool formats. A request permits at most eight model turns and 24 tool calls; when a limit is reached the model gets one final turn without tools so the answer finishes normally. File writes create immutable versions: text in SQLite, binary media on disk with a relative path in SQLite.

Compilation invokes `rustc` directly on temporary source files with a 30-second timeout and bounded diagnostics. It checks standard-library Rust as a library and **does not run programs, install packages, or build Cargo dependency graphs**. Compiler processes do not inherit API keys. On macOS the compiler runs in an OS sandbox that blocks network access, writes outside its temporary build directory, and reads outside an allow-list of the toolchain, the build directory, and system libraries. Other platforms fail closed, and the compile tool is not offered to the model there. This bounded compiler check is not a general-purpose code-execution service. General code answers can still be generated in other languages.

## Package

Produces `package/invisible-ai-server-<version>-<os>-<arch>.zip`, `package/invisible-ai-client-<version>-<os>-<arch>.zip`, `package/SHA256SUMS` for both, and a clean extracted copy of the server folder. `<version>` is the workspace version in `Cargo.toml` (`make version`). Each zip unpacks into one folder named like the archive and includes `.env.example`, `QUICK.md` (tutorial) and `README.md` (manual), whose sources are in `packaging/`. The server folder contains:

- `bin/server` and `bin/client` — backend and capture binaries.
- `bin/invisible-apple-ai`, `bin/invisible-mlx`, and `bin/mlx.metallib` — local AI workers and GPU kernels.
- `dist/`, documentation, licenses, `.env.example`, and the optional transcription script.
- **Start Invisible AI.command** — double-click to open the app. Keep its Terminal window open; Control-C stops both processes.

The installed app needs no Rust or Node.js for ordinary chat, capture and local inference. Apple AI requires macOS 26 with Apple Intelligence enabled. Download MLX model weights explicitly in Settings; weights and personal data are never bundled. Coding still needs the selected language's toolchain; optional speech transcription needs Python and its speech dependencies. The current archive is unsigned and not notarized.

Resources resolve relative to the executable, so the extracted folder can be moved. The default listener is `127.0.0.1:3000`. A non-loopback listener requires wallet access (`CWBBOT_ADMIN`) or `APP_TOKEN`. Local capture uses `<backend config>/capture-token` automatically. A remote client must receive a token from the owner through a private channel; its own `device-key` remains in the client configuration folder. Neither credential is included in packages or preference exports.

### Photo sets and follow-up comments

### Ready-to-run capture client

Run `make package` to produce `package/invisible-ai-client-<version>-<os>-<arch>.zip` alongside the server release. For a prefilled download, sign in and open **Dashboard → Download client.zip** (just `client` and `go.sh`, no folder). The backend inserts its detected **Tailscale IP** (including its listening port) and the **current authenticated wallet** into `go.sh`. Unpack on a matching computer, then run:

```sh
./go.sh
```

### Files and audio as AI context

Use **Add any file** in New thought or a chatroom to attach up to eight files, each up to 25 MB. Videos (MP4, MOV, M4V, WebM) can be up to 1 GB. The browser fingerprints the video, then sends it in 500 KB chunks straight from the picked file, and chat shows both steps. If the connection drops or the page reloads, attach the same video again and the upload continues where it stopped. Mix PDF, Word (DOCX), Excel (XLSX), PowerPoint (PPTX), OpenDocument (ODT/ODS/ODP), Markdown, plain text, source code, JSON/CSV, images, and sound files in the same message. Dotfiles such as `.gitignore` and files without an extension are accepted too. You can send the files without typing a question, or add instructions; in Multi Capture, **Send message** sends the staged files and screenshots together. Adding a file stages it without starting an AI answer.

Each attachment shows its size and context type. Text and Markdown are read directly; PDF and document text is extracted locally on the backend; audio is transcribed on submission and its transcript stays with the message for follow-up context. Staged audio can be previewed, and audio players do not preload downloads. Supported sound inputs include WAV, MP3, M4A, AAC, FLAC, Ogg/Opus, AIFF, and WebM audio; live transcription requires a configured Grok or Gemini backend. Demo mode uses an explicitly labeled transcript fixture.

Document extraction uses bounded text excerpts shared across the attached files. PDFs need selectable text and an unlocked copy; scanned PDFs can be supplied as page images. Spreadsheet formulas use saved results, and dates may appear as serial numbers. ZIP files provide a contents listing without opening nested files. Document macros and external links are never executed or fetched. Original files remain unchanged.

Other files can also be attached. **Metadata only** means there is no content decoder for that format: the AI receives its name, size, MIME type, and first-byte signature, not an interpretation of the file's contents. The original remains downloadable. Context is bounded by the existing history limits; clearing/deleting the chat removes room-owned files and transcripts across sessions.
